# Hyperborea

Revista de ensayo y creación (LabTIS, UNRN). Sitio estático en **Astro**, contenido en Markdown editado con **Sveltia CMS** sobre GitHub, búsqueda con **Pagefind**, alojado en **Cloudflare** (Workers con assets). Tres idiomas: `/es`, `/en`, `/fr`.

## Comandos

| Comando | Qué hace |
| --- | --- |
| `npm run dev` | Servidor de desarrollo (`localhost:4321`). La búsqueda no funciona aquí. |
| `npm run build` | Build completo: Astro + índice de búsqueda + redirecciones (`dist/`). |
| `npm run preview` | Sirve `dist/` (`localhost:4321`): búsqueda y redirecciones funcionan. |
| `npm run verify` | **Rutina de verificación completa** (ver abajo). `-- --offline` omite la comparación con Drupal. |
| `npm run a11y` | **Puerta de accesibilidad en un navegador real** (necesita `npm run build` y, la primera vez, `npx playwright install chromium`). `-- --only=paper` prueba solo las páginas cuya ruta lo contiene. |
| `npm run validate:html` | Valida el HTML de todas las páginas de `dist/` con html-validate (`.htmlvalidate.json`). |
| `npm run check:headers` | Cabeceras HTTP de seguridad sobre respuestas reales (`wrangler dev --local` sirviendo `dist/`). Contra el sitio en vivo: `-- --base=https://hyperborea-labtis.org` (úsalo al lanzar). |
| `npm run import:all` | Reimporta todo desde Drupal (solo migración; sobrescribe `src/content`). |

Requiere Node ≥ 22.23.4.

## Las URLs no se pueden romper

Las URLs son idénticas a las del sitio Drupal original (sin barra final: `/es/paper/slug`, `/es/Mare_Sugenum`, `/es/numero-8`, `/sites/default/files/...`).

- La URL de cada contenido sale de su `slug` (frontmatter). **No lo cambies en contenido publicado.** Si debes hacerlo, agrega la dirección anterior en `aliases`.
- `aliases` (frontmatter, lista de rutas que empiezan con `/`) crea una redirección 301 hacia ese contenido. No hay configuración central de redirecciones.
- `/{idioma}/node/{translationKey}` (URL de sistema de Drupal) se redirige solo desde `translationKey`.
- Los archivos subidos viven en `public/sites/default/files/` (misma ruta que en Drupal).
- `scripts/build-redirects.mjs` (parte de `npm run build`) genera las páginas de redirección y `dist/_redirects` (301 reales en Cloudflare) y **falla el build** si un destino no existe o un alias taparía una página real.
- `scripts/legacy-urls.txt` es una captura congelada de las 608 URLs públicas del sitio antiguo. `npm run verify` comprueba que todas respondan.

- Las páginas de palabras clave (`/es/taxonomy/term/976`, 956 términos × 3 idiomas) conservan su URL. El vocabulario es `src/data/keywords/` (un archivo JSON por término, `{ name, tid }`): `tid` es el id antiguo de Drupal (si dos términos antiguos compartían nombre se unieron en uno, con el otro id en `alsoTids`: el menú del CMS exige nombres únicos; refrescable con `npm run import:terms`, que conserva los términos creados en el CMS; en el CMS la colección tiene buscador y orden alfabético). Los editores eligen las palabras clave de cada paper en un menú desplegable alimentado por ese vocabulario, y suman términos nuevos en el CMS, en «Vocabulario de palabras clave»; un término nuevo no tiene `tid` y su página es `/es/taxonomy/term/<nombre-en-slug>`. Cada página lista los papers cuyo `keywords` incluye ese nombre. No están en el sitemap (tampoco estaban en el antiguo).

## Contenido

- `src/content/{papers,articles,pages}/{es,en,fr}/<slug>.md`
- Orden dentro de un número: `issueOrder`. Portada: `featured` (1–6). Nuevo número: agregar su año en `src/data/issues.ts`.
- Secciones válidas: ver `src/data/nav.ts` (el campo `section` es una lista cerrada en el CMS).
- Notas al pie: se escriben como párrafos que empiezan por `[1] texto` (o `[*]`, `[**]`), bajo un título «Notas», y se enlazan desde el texto con `[[1]](#01)`. No hace falta escribir ningún `id`: `src/plugins/footnotes.mjs` se lo agrega a la nota al generar la página (la migración desde Drupal había perdido esos destinos). Si un link `#NN` no tiene nota con ese número, `npm run verify` lo lista en el check 6b.
  - Cada nota numerada recibe el id `01`, `02`… (aunque nada la enlace). Por eso el campo `author` puede terminar en `[1]` (p. ej. `Anthony Stanton[1]`): la página del paper lo muestra como link a la nota 1 y los listados de número muestran solo el nombre (`src/lib/author.ts`).
- HTML dentro del Markdown: `src/plugins/sanitize.mjs` lo limpia al generar la página (lista blanca de etiquetas y atributos; se eliminan `<script>`, `<iframe>`, `on*=`, `style=` y URLs `javascript:`). Usa solo lo que el contenido ya usa (figuras, tablas, `<a id>`). `npm test` cubre las reglas y el check 6c de `verify` revisa `dist/`. Un enlace Markdown con espacios dentro de `<…>` (`[x](< https://…>)`) genera una URL rota con `%20`: escríbelo sin espacios.

## Editores (Sveltia CMS)

Entrar en `/admin/` con un **token personal de GitHub** (fine-grained, solo este repo, permisos *Contents* y *Pull requests* de lectura y escritura). Los permisos de cada editor son su rol en el repositorio: el equipo de editores con rol **Write**, el administrador con **Admin**.

Flujo editorial activado: cada guardado abre un pull request y pasa por Borrador → Revisión → Listo; **Publicar** lo fusiona en `main` y Cloudflare despliega solo. Proteger `main` (Settings → Branches): exigir pull request y que solo el administrador pueda aprobar/fusionar.

Edición local sin GitHub: `npm run dev`, abrir `/admin/index.html` en Chrome/Edge y elegir *Work with Local Repository*.

Las imágenes nuevas se convierten a WebP (máx. 2048 px) y se limitan a 20 MB. Para reducir imágenes pesadas ya existentes: `node scripts/optimize-images.mjs` (`--dry` para simular).

## Despliegue (Cloudflare Workers con assets)

El sitio es un Worker (`wrangler.jsonc`): sirve `dist/` como archivos estáticos y ejecuta `worker/index.ts` solo para `/api/*` (formulario de contacto). Está conectado a este repo desde el dashboard de Cloudflare (Workers Builds):

- **Build command:** `npm run build` (Astro + búsqueda + redirecciones; con solo `astro build` no hay buscador ni redirecciones del sitio antiguo).
- **Deploy command:** `npx wrangler deploy`.
- Rama de producción `main`. Cada PR genera una vista previa.
- Límites: 25 MiB por archivo (el mayor hoy: 14 MB), 20 000 archivos (hoy ~5400) y 2000 redirecciones (hoy ~1150).
- Dominio: `hyperborea-labtis.org` (sin `www`) es el principal, el mismo que usa el canonical del sitio antiguo; `www.hyperborea-labtis.org` debe redirigir (301) a él. Para asignar un dominio propio al Worker, el DNS de ese dominio debe estar en Cloudflare.

### Indexación y SEO (`<head>`)

- **Interruptor:** la variable de build `PUBLIC_INDEXABLE` decide si el sitio se indexa. Sin ella (por defecto) **todas las páginas son `noindex, nofollow` y `robots.txt` deshabilita todo**: es lo correcto para el dominio de desarrollo (`workers.dev`) y las vistas previas. **Al lanzar hay que poner `PUBLIC_INDEXABLE=true` en Workers Builds → Settings → Build → Variables** (solo la rama `main` se indexa; las vistas previas de otras ramas quedan `noindex` aunque la variable exista). `npm run verify` avisa (check 10b) cuando el build no es indexable.
- **Canonical y hreflang** salen de `src/lib/seo.ts` (con tests) y los emite `BaseLayout.astro`: siempre URLs absolutas con el dominio `hyperborea-labtis.org`. Las páginas con texto propio en su idioma se indexan y enlazan solo las traducciones **reales** (hreflang). Una copia sin traducir (texto en español bajo `/en` o `/fr`) lleva `canonical` a la página `/es`, `noindex, follow` y no aparece en el sitemap; al agregar la traducción real se indexa sola. Las páginas de palabras clave se indexan solo en `/es`; el buscador y el 404 son `noindex`.
- **Títulos y descripciones** (`src/lib/meta-text.ts` y `src/lib/descriptions.ts`, con tests): `BaseLayout` agrega « | Hyperborea » al título solo si el resultado sigue corto (un título académico largo va solo). Cada tipo de página tiene su descripción, localizada: paper = su `abstract` o, si falta, el primer párrafo del texto (hoy solo 6 de 137 papers tienen resumen cargado: cargarlo en el CMS mejora el resultado en buscadores); actividad y página institucional = título + primer párrafo; número, sección y palabra clave = frase con datos reales. Las páginas 2+ de un listado llevan « — Página N » en el título y en la descripción. Las palabras clave usan « Palabra clave: X » porque un paper puede llamarse igual. Los ids extra de Drupal de un término fusionado (`alsoTids`) conservan su URL pero llevan `canonical` al término principal y `noindex`. `npm run verify` (check 11) falla si una página no tiene título, si su descripción es vacía, demasiado corta o larga, o si se repite entre páginas.
- **Metadatos académicos y datos estructurados** (`src/lib/scholar.ts`, `src/lib/jsonld.ts`, `src/data/journal.ts`, con tests): cada paper lleva las etiquetas `citation_*` de **Google Scholar** (título, un `citation_author` por autor, fecha, revista, ISSN, número como volumen, idioma, palabras clave, URL del PDF) y JSON-LD `ScholarlyArticle` enlazado con su `PublicationIssue`, la revista (`Periodical`, ISSN 2618-4397) y el editor (LabTIS). La portada de cada idioma lleva `WebSite`, los números `PublicationIssue`, las actividades `Article`, las páginas institucionales `WebPage`, y las páginas internas `BreadcrumbList`. **La fecha:** si el paper tiene `publishedDate` se usa completa; si no, solo el **año de su número** (`src/data/issues.ts`; coincide con la fecha real en los 53 papers que la tienen), sin inventar mes ni día. **Varios autores:** el campo `author` admite «A y B», «A & B» o «A; B» (un autor por etiqueta; la afiliación solo se adjunta si hay uno). Las copias sin traducir y los duplicados no llevan ni etiquetas ni JSON-LD. Los datos de la revista están en `src/data/journal.ts`. `npm run verify` (checks 12 y 12b) valida las etiquetas, el JSON-LD y que cada PDF citado exista; **avisa de los papers sin `author`**: Scholar necesita un autor para indexarlos (hoy 7: sus nombres están en el cuerpo del texto; al cargar el campo `author` aparecerá también en la firma de la página).
- **Sitemap** (`sitemap-index.xml`): solo páginas indexables. `robots.txt` lo genera `src/pages/robots.txt.ts`. **`lastmod`** solo donde hay una fecha real: la fecha de publicación del texto (o, si falta, la de creación), el número = su paper más reciente, la portada = el texto más reciente. Los listados y las páginas institucionales no llevan `lastmod`: una fecha inventada enseña a los buscadores a desconfiar de las demás (check 14).
- **RSS** (`/{lang}/rss.xml`, `src/lib/rss.ts` con tests): título y descripción en cada idioma, `atom:link rel="self"`, `lastBuildDate` (la fecha del ítem más reciente, para que el build sea reproducible), `dc:creator` por autor. Cada ítem apunta a la URL canónica (un texto solo en español apunta a su `/es` en todos los feeds). Check 15.
- **404** (`src/pages/404.astro`): una sola página para todos los idiomas (Workers sirve un único 404), por eso saluda en español, inglés y francés, es `noindex` y no tiene canonical ni hreflang (check 16).
- **Enlaces propios en el contenido:** los enlaces a este sitio se escriben **relativos** (`/es/paper/x`, `/sites/default/files/…`), nunca con `https://hyperborea-labtis.org/…`: los absolutos se rompen en las vistas previas y en el dominio de desarrollo. Si pegas uno en el CMS, `npm run verify` falla (check 13) y **`npm run fix:links`** lo convierte (reglas en `src/lib/own-links.ts`). Solo cambia el *destino* del enlace: la URL visible de una cita («URL: https://…») y el `sourceUrl` del frontmatter quedan como están. El check 6 revisa además que cada enlace relativo llegue a una página o archivo que existe.
- **Resúmenes** (campo `abstract`, se muestra antes del texto y alimenta la meta description y el JSON-LD). Si lo redactó la redacción y no el autor, lleva `abstractSource: editorial` y la página imprime «Resumen elaborado por la redacción» (en EN/FR, su equivalente). 93 papers los redactó la redacción con IA a partir del texto completo y quedan **pendientes de revisión editorial**: se encuentran buscando `abstractSource: editorial`, y basta cambiarlo a `author` (o reemplazar el texto desde el CMS) cuando el autor envíe el suyo. Los papers que ya traen un «Resumen» del autor dentro del texto no llevan resumen de la redacción, y si además tienen `abstract` en el frontmatter, la página no imprime la sección (`src/lib/abstract.ts`, con tests) para no mostrarlo dos veces. Check 17: largo razonable (30–300 palabras), un solo párrafo sin Markdown, y la sección y la etiqueta presentes en las tres lenguas.
- **Artículos relacionados** (bloque al final de cada paper, `src/lib/related.ts` con tests): hasta 4 papers que comparten palabras clave (cada una pesa 10) o el mismo número (+2) y sección (+1); a igualdad, el más reciente. Da enlaces internos entre textos del mismo tema; queda fuera del índice de búsqueda (`data-pagefind-ignore`).
- **Calidad del HTML generado** (check 6c): ningún enlace sin texto ni nombre accesible (`[](url)` del import de Drupal) y ningún destino sin barra inicial (`href="alguien@mail.com"` sin `mailto:`, `href="www.sitio.cl"` sin `https://`), porque se resuelven contra la página actual y no llevan a ningún lado. Un solo `<h1>` por paper y actividad (check 9d): dentro del texto, los títulos empiezan en `##`. Las imágenes incrustadas (`data:`) llevan texto alternativo.
- **Accesibilidad estructural** (check 18, `src/lib/page-structure.ts`, con tests): en las 3.583 páginas del `dist` hay un solo `h1`, todo `<img>` tiene `alt`, el primer enlace es «Pasar al contenido principal» (salto a `#main-content`), no hay `id` repetidos y todo atributo `lang` es válido; en portadas, listados y secciones los encabezados además no saltan de nivel. Las tarjetas tienen un solo enlace (el del título; la imagen es decorativa y no entra en el teclado). Las imágenes destacadas son decorativas por defecto: para describirlas hay que completar «Descripción de la imagen destacada» (`heroAlt`) en el CMS. El texto que está en otro idioma que la página (copias EN/FR sin traducir) lleva su propio `lang`.
- **Teclado, movimiento y alto contraste** (check 19 y el 18): el submenú es un botón con `aria-expanded`/`aria-controls` (Enter/Espacio abre, `Esc` cierra también el abierto por el mouse y devuelve el foco, clic fuera o salir con Tab lo cierra); `scroll-padding-top` con la altura real de la cabecera fija evita que tape el elemento enfocado (WCAG 2.4.11); los enlaces de idioma miden al menos 24 × 24 px (2.5.8); hay reglas para `prefers-reduced-motion` y `forced-colors` (alto contraste de Windows). Ningún script arma HTML desde texto (`innerHTML` y similares): los extractos de la búsqueda se construyen con nodos y el check 19 lo vigila junto con esas reglas de CSS. El formulario de contacto marca los campos inválidos (`aria-invalid`), anuncia el error con `role="alert"` y lleva el foco al primero.
- **Contraste y foco** (check 20, `src/lib/contrast.ts`, con tests): el amarillo de marca `#d8b200` rinde 2,04:1 sobre blanco, así que solo se usa como fondo y como texto sobre el negro de la cabecera. El texto amarillento sobre claro usa `--hb-yellow-text` (`#7a6200`, 5,9:1; `--hb-yellow-large` para títulos grandes en negrita), el texto del footer es negro, los bordes de campos usan `--hb-control-border` (`#767676`) y el gris de texto `--hb-muted` (`#595959`). El check falla si un token baja de su umbral (4,5:1 texto, 3:1 grande y bordes) o si el amarillo de marca vuelve a colorear texto fuera de la cabecera. Todo control enfocado con teclado lleva un anillo de 3 px (tinta sobre blanco, amarillo en la cabecera, negro en el footer: `--hb-focus`) y los enlaces dentro del texto van subrayados, para no depender solo del color (WCAG 1.4.1).
- **Puerta de accesibilidad en CI** (`scripts/a11y.mjs`, job `a11y` de GitHub Actions; conviene marcarlo como check requerido junto a `verify`): Playwright maneja Chromium contra el sitio ya construido, servido con `wrangler dev --local` (mismas cabeceras, redirecciones y página 404 que producción). Sobre una muestra fija de 20 páginas (3 portadas, un número, papers con y sin resumen, actividad, páginas institucionales, listados, palabra clave, búsqueda con resultados, contacto, 404 y copias EN/FR sin traducir) comprueba: **axe-core** con las etiquetas WCAG 2.0/2.1/2.2 A y AA más buenas prácticas, también con el submenú abierto; **reflow** a 320 px sin scroll horizontal (1.4.10); **espaciado de texto** forzado sin recortes (1.4.12); el primer Tab es el enlace de salto y mueve el foco a `<main>`; cada parada de Tab muestra un indicador de foco (también con `forced-colors`) y la cabecera fija no la tapa ni hacia adelante ni con Shift+Tab (2.4.7, 2.4.11); el submenú se abre con el teclado, Tab entra y Esc lo cierra devolviendo el foco; con `prefers-reduced-motion` no corre ninguna animación; y ninguna página viola la CSP ni lanza errores de script. Cada comprobación se probó rompiendo a propósito el `dist` (sin enlace de salto, `outline: none`, `scroll-padding-top: 0`, `min-width`, script en línea, `Esc` roto…). El mismo job corre **html-validate** sobre las 4.161 páginas: 0 errores. Los filtros de la búsqueda (`SearchFilter.astro`) y las tablas importadas (el sanitizador descarta `align`, `cellpadding`… y conserva el centrado como clase) se ajustaron para que el HTML sea válido.
- **Cabeceras de seguridad** (check 21, `scripts/build-headers.mjs`, `scripts/check-headers.mjs`, `src/lib/csp.ts` y `src/lib/headers-check.ts`, con tests): Astro escribe la CSP como `<meta>` en cada página, pero los validadores públicos (securityheaders.com, MDN Observatory) leen la **cabecera**. Al final de `npm run build`, `build-headers.mjs` lee la política de las 3.586 páginas (comparten una sola; pueden diferir solo en los hashes de scripts, cualquier otra diferencia rompe el build), la revisa (sin `unsafe-inline`/`unsafe-eval`, sin comodines, `object-src 'none'`, `base-uri`) y la agrega a `dist/_headers` para `/es`, `/en`, `/fr` y lo que cuelga de ellos, **nunca para `/*`**: Cloudflare junta todas las reglas que coinciden y la política estricta rompería `/admin`, que tiene la suya. El resto de cabeceras (HSTS de un año con subdominios y **sin `preload`**, `nosniff`, `X-Frame-Options`, `Referrer-Policy`, COOP, `Permissions-Policy` con `browsing-topics=()`) está en `public/_headers`. El check 21 vigila el archivo y `check:headers` vigila las respuestas reales; ambos se probaron rompiendo la política a propósito (bloque ausente, política distinta, CSP bajo `/*`, página sin `<meta>`, `/admin` sin su política, `unsafe-inline`, `preload`). Si cambia el dominio o se añade un script en línea, el build recalcula los hashes solo. `Cross-Origin-Resource-Policy` no se activa: la fuente RSS y las imágenes se enlazan desde fuera.
- **Redirecciones** (check 9a): ninguna redirección, de `_redirects` o de las páginas stub, termina en otra redirección (cadena), en sí misma (bucle) ni en una página que no existe. `www` → dominio sin `www` y HTTP → HTTPS se configuran en Cloudflare al lanzar (ver la lista de lanzamiento).
- **Iconos e imagen social** (`favicon.ico`, `apple-touch-icon.png`, `og-default.png`) son **provisionales**: se derivan del único logo disponible (GIF de 300×80). Cuando llegue el logo vectorial, reemplazar la fuente y ejecutar `node scripts/build-brand-assets.mjs`. Las páginas con imagen propia (papers, actividades) usan esa imagen en `og:image`.

### Formulario de contacto (`/es/contact`)

`worker/index.ts` envía el correo con Cloudflare Email Service (binding `send_email` llamado `EMAIL`, ya declarado en `wrangler.jsonc`) y lo protege con **Cloudflare Turnstile**, un límite de **5 envíos por minuto por IP** (binding `CONTACT_LIMITER`), verificación de `Origin` (solo el propio sitio), tope de 16 KB y honeypot. El destinatario es siempre `CONTACT_TO`; nada del formulario lo controla. Para activarlo:

1. Dominio habilitado para envío: `npx wrangler email sending enable <dominio>` (debe estar en Cloudflare).
2. **Widget de Turnstile** (dashboard → Turnstile → Add widget, con los hostnames del sitio). La **clave del sitio** es pública: va como variable de build `PUBLIC_TURNSTILE_SITEKEY` (Workers Builds → Variables). Sin ella la página muestra «formulario no disponible» en lugar del formulario: ese es el estado *suspendido*.
3. Tres **secretos** del Worker (no van en el repo, que es público): `CONTACT_TO` (buzón que recibe los mensajes), `CONTACT_FROM` (dirección del dominio habilitado) y `TURNSTILE_SECRET` (clave secreta del widget). `npx wrangler secret put CONTACT_TO`, etc., o en el dashboard: Worker → Settings → Variables and Secrets → tipo *Secret*. Si falta alguno el Worker responde 503 (`not_configured`).

Probar en local: copiar `.env.example` a `.env` con la clave de pruebas de Turnstile (`1x00000000000000000000AA`, siempre aprueba), crear `.dev.vars` (ignorado por git) con `CONTACT_TO`, `CONTACT_FROM` y `TURNSTILE_SECRET=1x0000000000000000000000000000000AA`, ejecutar `npm run build` y `npx wrangler dev`. Los tipos del Worker (`Env`) se generan con `npm run types` desde `wrangler.jsonc` y `worker/secrets.example` (nombres de los secretos); no se escriben a mano. No declares los secretos con `secrets.required` en `wrangler.jsonc`: haría fallar el despliegue mientras falte alguno. Los errores del Worker se ven con `npx wrangler tail` (sin datos personales en los logs).

## Verificación

`npm run verify` ejecuta: build + type check, conteos contra Drupal, integridad de archivos, frontmatter/slugs/secciones, i18n, enlaces internos (sin barra final, sin rotos; y avisa de los `#enlaces` dentro de una página sin destino), configuración del CMS, índice de búsqueda y **paridad de URLs con el sitio antiguo**. Sale con código 1 si algo falla.

### Buscador (`/es/buscar`)

Búsqueda de texto completo con Pagefind (índice estático generado por `npm run build`; en `npm run dev` no hay índice). Se puede acotar por **Tipo** (paper / actividad / página), **Sección** y **Número** (estas dos solo existen en papers). Los filtros salen de `<meta data-pagefind-filter>` en las plantillas de paper, actividad y página, y se reflejan en la URL (`?q=…&tipo=…&seccion=…&numero=…`).

### Portada, secciones y paginado

- **Portada (`/es`)**: los 6 últimos papers de las secciones Mare Sugenum, Kino LabTIS, Manet et manebit y 41º 9’ S 71º 8’ W (por fecha; sin actividades ni Afinidades electivas) y un botón «Ver más» que lleva a `/es/posts-3-col`.
- **`/es/posts-3-col`**: todas las publicaciones (papers y actividades), de la más nueva a la más vieja, 6 por página con paginador. La página 1 es `/es/posts-3-col`; las demás, `/es/posts-3-col/2`, `/3`… Las URLs antiguas del paginado de Drupal (`?page=N`) redirigen a la página nueva.
- **Secciones**: Mare Sugenum, Kino LabTIS, Manet et manebit y 41º 9’ S 71º 8’ W muestran solo el número actual. **Afinidades electivas** (`allIssues: true` en `src/data/nav.ts`) muestra todos sus papers de todos los números, el más nuevo primero, 6 por página (`/es/Afinidades_electivas`, `/2`, `/3`…).
- **Orden "más nuevo primero"**: la portada, `/posts-3-col` y Afinidades electivas ordenan por `created` (fecha y hora de creación que tenían en Drupal, guardada en cada paper y actividad). Así el orden coincide con el sitio antiguo al minuto; `publishedDate` solo tiene el día y no alcanza (varios papers de un mismo número comparten fecha). Contenido nuevo creado en el CMS puede dejar `created` vacío: se usa `publishedDate`.
